# Control de Obra Pro - Project Instructions

## Overview
ERP de construcción y gestión de obras para operaciones en Colombia (moneda COP).
Stack: Next.js 14 + MySQL + Prisma + NextAuth.js

## Tech Stack
- Next.js 14 (App Router), TypeScript, Tailwind CSS, Prisma ORM, **MySQL 8.0**
- NextAuth.js (credentials), almacenamiento local de archivos (public/uploads)
- Radix UI components, Lucide icons
- Arquitectura modular: `modules/<nombre>/{service,queries,validations,types}.ts`
- Capa MySQL: `database/mysql/{functions,triggers,procedures,views}.sql`
- Skills locales empaquetadas: `Skills/*.skill`

## Skills Aplicadas (Carpeta Skills)

Estas skills deben considerarse activas para el trabajo diario del proyecto:

1. **fullstack-engineer**
	- Skill por defecto para implementación, fixes, refactors y mejoras end-to-end.
	- Flujo obligatorio: diagnóstico -> diseño -> implementación -> verificación.

2. **software-architecture**
	- Activar en decisiones de arquitectura, modularización, separación de responsabilidades y escalabilidad.
	- Entregables esperados: análisis de riesgos, propuesta estructural y roadmap por fases.

3. **data-structures-optimizer**
	- Activar cuando haya cuellos de botella de rendimiento, búsquedas repetidas o colecciones ineficientes.
	- Exigir comparación de complejidad (antes/después) y trade-offs de memoria vs velocidad.

4. **memory-tester**
	- Activar en ciclos de depuración o correcciones repetidas para evitar regresiones y errores ya resueltos.
	- Mantener bitácora de errores/fixes de la sesión y reutilizar soluciones previas antes de proponer nuevas.

5. **claude-code-context-manager**
	- Activar cuando la conversación sea extensa o aparezcan síntomas de pérdida de contexto.
	- Aplicar compactación preventiva de contexto y preservación de decisiones clave del proyecto.

## Protocolo de Activación

- Si una tarea mezcla varias áreas, combinar skills (por ejemplo, fullstack-engineer + software-architecture).
- Si hay conflicto entre recomendaciones, priorizar: seguridad -> arquitectura -> corrección funcional -> rendimiento.
- Antes de cambios grandes, registrar supuestos y riesgos; después, validar impacto y posibles regresiones.
- Para tareas de rendimiento, reportar siempre complejidad Big-O y evidencia del cuello de botella.
- Para tareas de debug, revisar primero historial de correcciones de la sesión antes de repetir un fix.

## Key Patterns
- Subcontractor documents: CEDULA, RUT, CAMARA_COMERCIO, CERTIFICADO_BANCARIO
- Extended contractor/supplier info: legal rep, financial info, 3 commercial references
- Currency: COP (Colombian Pesos), no decimals
- Auto-generated numbers: PRY-, CTR-, PAG-, EMP-, CLI-, COT-
- Prisma singleton cached in globalThis for both dev and prod
- Sequential DB queries on dashboard to avoid connection pool exhaustion
- Client components use useParams() hook (not use(params))
- Business logic lives in `modules/<name>/service.ts`, not in API routes
- API routes call service functions; service calls queries; queries use Prisma
- MySQL stored procs via `prisma.$executeRaw`, views via `prisma.$queryRaw`

## MySQL DB Layer
- `sp_recalculate_budget(budgetId)` — recalculates all budget totals in cascade
- `sp_approve_payment(paymentId, approverId, level, comments, OUT status)`
- Views: v_project_summary, v_financial_summary, v_payment_dashboard, etc.
- Triggers auto-update layer/budget totals on BudgetItem changes
